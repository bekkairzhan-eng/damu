## 1. Суть задачи

Перенести постановку, мониторинг и оценку KPI топ-менеджмента из Excel и переписки в единую систему. Расчёт должен быть прозрачным и связанным с годовой премией (**STI**).

| Параметр | Значение |
|---|---|
| Заказчик и владелец продукта | C&B Холдинга |
| Охват | Все сотрудники с бонусным фондом, **~200 человек** |
| Цикл | Календарный год (1 января – 31 декабря), оценка ежеквартально и по итогам года |
| Ключевой срок | Формирование карт KPI на 2027 год **начинается до конца 2026** |
| Платформа | «Новая система на базе имеющейся внутренней платформы [указать]» |
| Исполнитель | «IT-подразделение [уточнить]» |

Полный цикл: **каталог → карты → согласование → мониторинг → оценка → передача в расчёт премии.**

## 2. Термины

| Термин | Смысл |
|---|---|
| KPI | Показатель с формулой, источником данных и периодом оценки |
| Каталог KPI | Справочник всех утверждённых KPI группы |
| STI | Краткосрочная (годовая) премия по итогам KPI |
| Мотивационный лист | Карта KPI сотрудника на год. Образец — `шаблон_KPI.xlsx` (**не приложен**) |
| Перспектива ССП (BSC) | Финансы · Клиенты · Внутренние бизнес-процессы · Обучение и развитие |
| RCD | Тип KPI: RUN — текущая деятельность, CHANGE — изменения и развитие |
| Метод расчёта | Прямой (больше — лучше) · Обратный (меньше — лучше) · Бинарный (да/нет) · Качественный (оценка руководителя) |
| Вес | Доля KPI в итоге, %. Сумма весов в листе = 100% |
| Исполнение | Факт к цели по методу, ограничено 80–120% |
| Результат KPI | Исполнение × вес |
| Итоговый результат | Сумма результатов, ограничено 50–120% |
| КТУ | Доля отработанных календарных дней цикла (по датам приёма и увольнения из ERP), не больше 100% |
| Бюджет БФ | Бонусный фонд сотрудника. Вносит C&B вручную |

## 3. Роли (по ТЗ)

Общее правило: руководитель видит только свою карту и карты прямых подчинённых.

| Роль | Кто | Права |
|---|---|---|
| Администратор системы | C&B Холдинга | Каталог, шаблоны, правила расчёта, циклы, маршруты; все компании |
| C&B компании | C&B компаний группы | Бюджет БФ, оргструктура, подписанты и согласующие, кабинет расчёта — по своей компании |
| HR | HR дивизиона или управления | Просмотр карт и итогов только своего дивизиона или управления |
| Руководитель | Непосредственный руководитель | Ставит KPI, оценивает подчинённых, согласует |
| Участник | Сотрудник с бонусным фондом | Своя карта, комментарии, ознакомление, заявка на удержание в «Жулдызай» |
| Владелец факта | Финблок (финансовые KPI), руководитель (остальные) | Ввод и подтверждение факта |
| Комитет | [уточнить] | Сводные итоги, включая суммы к начислению |
| Системный администратор | IT | Пользователи, интеграции, журналы. **Без доступа к содержанию оценок** |

## 4. Функциональные требования (ТЗ)

### 4.1. Каталог KPI
- Карточка: код, наименование, цель (TARGET), перспектива ССП, RCD, единица измерения, метод расчёта, периодичность, источник данных, владелец факта.
- Группировка по ССП и по компаниям.
- **Версионность:** изменение формулы создаёт новую версию, история сохраняется.
- Статусы: черновик, действующий, архив.

### 4.2. Карта KPI
- Повторяет форму мотивационного листа: шапка (компания, ФИО, должность, год), таблица KPI, итог, блок КТУ и суммы к начислению, условия расчёта, подписи.
- Строка: ССП, №, цель, KPI, RCD, ед. изм., метод, вес %, цель, факт, исполнение, результат, примечание.
- Одно целевое значение на KPI.
- **Сумма весов = 100%**, иначе карту нельзя отправить на согласование.
- Единица измерения однозначна и совпадает с формулировкой KPI — это проверяет C&B.
- Количество KPI в карте — [уточнить]; в образце 7.
- Создание: **из шаблона по должности** или **копированием карты прошлого цикла**.
- **Каскадирование:** KPI группы → KPI компании → KPI сотрудника, связь видна.
- Несколько карт за цикл (перевод, смена должности), каждая действует в своём периоде [порядок расчёта итога — уточнить].
- После утверждения карта не меняется.

### 4.3. Согласование
- Единый маршрут: **сотрудник → руководитель → HR (C&B) → утверждение CEO Холдинга**. Исключения для отдельных сотрудников и компаний настраивает C&B.
- Согласующие и подписанты берутся из оргструктуры ERP; C&B может переназначить вручную.
- Действия: согласовать или вернуть на доработку с комментарием.
- Эскалация: при просрочке задача уходит вышестоящему [срок уточнить].
- Подписание — подтверждением в системе, без ЭЦП. Печатная форма с полями подписей.
- Уведомления по e-mail и в интерфейсе.
- После утверждения карта блокируется.

### 4.4. Мониторинг
- На старте (карты 2027) вносятся только планы, факта нет.
- Факт вводится вручную: финансовые KPI — финблок, остальные — руководитель. Автозагрузка — следующий этап.
- Оценка ежеквартально и по итогам года.
- Цвета: < 80% · 80–100% · ≥ 100%.

### 4.5. Расчёт и оценка — формулы

**Исполнение KPI по методам:**

| Метод | Формула |
|---|---|
| Прямой | факт / цель |
| Обратный | 1 + (цель − факт) / цель; отрицательное значение → 0% |
| Цель = 0 | факт 0 → 100%; факт > 0 → 0% |
| Бинарный | выполнено → 100%; не выполнено → 0% |
| Качественный | оценка руководителя в % [шкала — уточнить] |

**Ограничения и итог:**
- исполнение < 80% → **0%**; > 120% → **120%**;
- факт не внесён → статус «Пусто», результат 0;
- результат KPI = исполнение × вес;
- итог = сумма результатов; **< 50% → STI не выплачивается**; > 120% → 120%;
- округление исполнения, результата и итога — до 0,1%.

**КТУ** = отработанные дни / дни цикла:
- начало — более поздняя из двух дат: приём (ERP) или начало цикла;
- конец — более ранняя из двух дат: увольнение (ERP) или конец цикла;
- не больше 100%, округление до целого процента.

**К начислению = бюджет БФ × итоговый результат × КТУ.**

Дополнительно:
- удержание 2% в Корпоративный фонд «Жулдызай»: система создаёт сотруднику задачу-заявку;
- расчёт попадает в кабинет HR/C&B; C&B может округлить и скорректировать суммы с обоснованием, всё журналируется;
- следующий этап — заявка на премирование в BPM.

**Проверка на примере из мокапа ТЗ (рисунок 10.1)** — формулы сходятся:

| KPI | Вес | Цель | Факт | Исполнение | Результат |
|---|---|---|---|---|---|
| Выручка, млрд тг | 15% | 2 950 | 3 068 | 104,0% | 15,6% |
| ROS, % | 15% | 15 | 13 | 86,7% | 13,0% |

### 4.6. Дашборды и отчёты
- **Личный кабинет сотрудника:** карта, факт, исполнение, история.
- **Кабинет HR/C&B:** реестр карт, бюджет БФ, расчёт сумм, корректировки, выгрузка.
- **Сводный дашборд комитета:** исполнение по компаниям и сотрудникам, итоги и суммы, статус согласования.
- **Печатная форма** мотивационного листа в Excel и PDF.
- **Отчёты:** реестр карт, статус согласования, итоги квартала и цикла, журнал изменений.

**Мокап дашборда комитета (рисунок 10.2):**
- фильтры: цикл, компания, перспектива ССП; кнопка «Выгрузить в Excel»;
- плитки: «Карты утверждены 18 из 20», «Средний итог 95,3%», «STI не выплачивается — 1 руководитель» (выделена красным), «На согласовании 2 карты»;
- горизонтальные бары «Итоговый результат по компаниям» с линиями «порог 50%» и «цель 100%»;
- таблица «Руководители: итог и статус» (ФИО, компания, итог, статус). Итог ниже 50% подсвечен красным.

## 8. Разбор HTML-макета (MVP)

### 8.1. Общее
- Заголовок «KPI · STI 2027», подпись «MVP · пример: функция HR», «BI Group · конфиденциально».
- Наверху переключатель ролей («Вы вошли как …») и кнопка «Вернуть пример к исходному» (сброс демо-данных).
- Пять вкладок: **Пирамида каскада · Исполнение команды · Дашборд · Карты KPI · Каталог KPI.** Плюс печатная форма и модалка «Новая карта».

### 8.2. Роли в макете (отличаются от ТЗ)

| id | Роль | Зона видимости |
|---|---|---|
| `hrdh` | HRD Холдинга | Всё |
| `hrdc` | HRD компании (C1 CA) | Своя компания |
| `hrdd` | HRD дивизиона (Дивизион 1) | Свой дивизион |
| `hrbp` | HRBP (Управление 1) | Свои управления |
| `cb` | C&B (проверка) | Всё |

Карта Холдинга видна всем ролям. Карта компании видна только своей компании.

### 8.3. Статусы и маршрут согласования
Статусы: `draft` Черновик · `returned` На доработке · `hrdd` У HRD дивизиона · `hrdc` У HRD компании · `cb` На проверке C&B · `hrdh` У HRD Холдинга · `approved` Утверждена.

**Инициатор карты — HR, а не сотрудник и не руководитель.** Кто именно, зависит от того, где находится владелец карты:
- карта Холдинга → HRD Холдинга;
- карта компании → HRD компании;
- сотрудник в управлении HRBP → HRBP;
- сотрудник в дивизионе → HRD дивизиона;
- сотрудник компании → HRD компании;
- остальные → HRD Холдинга.

Маршрут собирается динамически: `инициатор → [HRD дивизиона] → [HRD компании] → Проверка C&B → Утверждение HRD Холдинга → Утверждено`.

Действия:

| Этап | Кнопки |
|---|---|
| Черновик / доработка (инициатор) | «Отправить HRD дивизиона / HRD компании / на проверку C&B». Неактивна, пока есть ошибки валидации |
| HRD дивизиона, HRD компании | «Согласовать», «Вернуть на доработку» |
| C&B | «Проверено», «Вернуть». Подсказка: «C&B проверяет веса, единицы измерения, методы расчёта и связь…» |
| HRD Холдинга | «Утвердить», «Вернуть» |
| Утверждена | «Карта утверждена и не изменяется» |

Вернуть без комментария нельзя («Напишите, что исправить — без комментария вернуть нельзя»). Последний комментарий возврата показывается баннером на карте. Все действия пишутся в «Историю» (дата, кто, действие, комментарий).

### 8.4. Валидация карты
- нет ни одного KPI → «Добавьте хотя бы один KPI»;
- сумма весов ≠ 100% (рядом шкала весов: зелёная при 100, красная при превышении);
- в строке не выбран KPI, не указана цель или вес;
- **один KPI добавлен дважды.**

### 8.5. Каскад
- Каждая строка карты может ссылаться на строку карты уровня выше (поле `parent`).
- Источники («Каскад от»), в порядке приоритета: карта **непосредственного руководителя** → карта **функционального руководителя** (`fmgr`, пунктирное подчинение) → карта компании → карта Холдинга.
- Кнопка «Взять KPI уровня выше» и опция «Каскадировать KPI уровня выше» при создании карты.
- На карте показываются процент «Связано с уровнем выше» и счётчик «каскадирован ниже: N» у каждой строки.

### 8.6. Создание карты (модалка)
- «Для кого»: сотрудники **без карты** в зоне роли, для которых роль — инициатор. HRD компании также может создать карту компании.
- «Основа»: «Каскадировать KPI уровня выше» или «Пустая карта».
- Вариантов из ТЗ «шаблон по должности» и «копия прошлого цикла» в макете нет.

### 8.7. Вкладки
1. **Пирамида каскада** — уровни: Холдинг → Компании → КЦ Холдинга («создаёт стратегию и методологию») → Компания («принимает и адаптирует») → Дивизион («внедряет и контролирует») → Управление («исполняет»). Внутри уровня карты сгруппированы по функциям (HR, C&B, L&D, Рекрутинг), у каждой функции есть захардкоженная «доля» на уровне (`SHARE`, например HR 20/40/25/15%). По клику на цель видно, у кого она есть и как идёт вниз; связанные подсвечиваются, остальные приглушаются. Есть кнопки «Открыть карту» и «Снять выделение».
2. **Исполнение команды** — выбор квартала (Q1–Q4, по умолчанию Q3), фильтр компании, переключатель «Показать всех / Только с рисками»:
   - по каждому человеку — плитки KPI с цветом (< 80 / < 100 / ≥ 100), «цель · факт», исполнение, результат, тренд по кварталам;
   - сводка: средний итог, сколько человек ниже 50%, сколько KPI ниже 80%;
   - «Карта KPI не создана» для тех, у кого её нет;
   - видны только подчинённые по дереву (для C&B — все).
3. **Дашборд (каскадирование)** — фильтры по компании и цели Холдинга:
   - плитки «Сотрудников с бонусным фондом», «Карты созданы X из Y», «Карты утверждены», «KPI связаны с уровнем выше %»;
   - дерево целей «Холдинг → компании → руководители → сотрудники»;
   - отдельный блок «KPI без связи с уровнем выше»;
   - таблица сотрудников: ФИО, должность, компания, руководитель, статус карты, число KPI, связь, итог.
   - **Это не дашборд комитета из ТЗ.**
4. **Карты KPI** — слева реестр (счётчики: всего / черновики / согласование / утверждено; фильтры по уровню, компании, статусу). Справа карта:
   - шапка, уровень, статус, кнопка «Печатная форма»;
   - трек маршрута, шкала весов, таблица;
   - у утверждённой карты — факт, исполнение, результат и блок «Расчёт STI»: итоговый результат, КТУ (дни, дата приёма), бюджет БФ (вводит только C&B), к начислению, фонд «Жулдызай» 2%. Если итог выше 120% — «рассчитано X%, учтено 120%». Если ниже 50% — «STI не выплачивается».
   - внизу история.
5. **Каталог KPI** — таблица: KPI, ед. изм., ССП, RCD, метод, «в картах» (сколько карт используют). Добавлять может только C&B (название, ед. изм., ССП, RCD, метод). У остальных — «Только просмотр».

### 8.8. Печатная форма
- Шапка, «Утверждаю», таблица с колонками «Каскад от», «Исполнение», «Результат».
- Блок «Условия расчёта STI-целей»:
  - исполнение ниже 80% → 0%, выше 120% → 120%;
  - итог ниже 50% → STI не выплачивается, выше 120% → 120%;
  - результаты округляются до 0,1%;
  - КТУ считается в календарных днях (365 дней в году), округляется до целого процента и не больше 100%.
- «Настоящим подтверждаю удержание 2% в Корпоративный фонд «Жулдызай» от размера годового бонусного фонда».
- «Дата ознакомления «___» ________ 2027 г.»

### 8.9. Кто вводит факт (макет)
Только на утверждённых картах сотрудников. Вводят **C&B**, а также **HRBP и HRD компании** в своей зоне. Бинарный KPI — выбор «Да / Нет», качественный — процент напрямую.

### 8.10. Модель данных макета (пригодится при переносе)
```
catalog:   { id, name, unit, bsc, rcd: 'RUN'|'CHANGE', method }
employees: { id, name, position, func, company, level, division, dept, unit,
             manager, fmgr /*функциональный рук.*/, hire, fire }
cards:     { id, type: 'holding'|'company'|'emp', owner, status, budget,
             history: [{date, who, action, comment}],
             rows: [{ uid, kpi, weight, target, parent /*uid строки выше*/,
                      fact, qf: {Q1, Q2, Q3, Q4} }] }
```
Демо-данные:
- 14 KPI в каталоге (все HR-тематики);
- 20 сотрудников в компаниях «КЦ Холдинга», «C1 CA», «C2 North»;
- 1 карта Холдинга, 2 карты компаний, карты сотрудников во всех статусах;
- факты Q1–Q3 у части утверждённых карт;
- у одного сотрудника дата приёма 01.02.2027, чтобы показать КТУ < 100%.

### 8.11. Технические наблюдения по макету
- **Факт хранится в двух местах:**
  - `row.fact` (годовой) — его показывает карта и печатная форма;
  - `row.qf.Q1..Q4` (квартальный) — его показывает «Исполнение команды».

  В демо годовой факт заполнен только у одной карты, поэтому в карте почти везде «Пусто», хотя в «Исполнении команды» данные есть. Нужно решить, как факт ведётся по кварталам и как из них получается годовой.
- Расчёт (`execOf`, `calc`, `ktuOf`) реализован точно по формулам ТЗ, его можно переносить почти без изменений.
- Нет: эскалации, уведомлений, версий и статусов каталога, нескольких карт за цикл, шаблонов по должности, копирования прошлого года, корректировок сумм C&B, выгрузок Excel/PDF (только печать из браузера), переключения языков, личного кабинета сотрудника, дашборда комитета, заявки в «Жулдызай».

## 9. ТЗ и макет: сравнение

| Тема | ТЗ | HTML-макет |
|---|---|---|
| Маршрут | Сотрудник → Руководитель → HR (C&B) → CEO Холдинга | HRBP → HRD дивизиона → HRD компании → C&B → HRD Холдинга |
| Кто составляет карту | Руководитель ставит KPI подчинённому | HR (HRBP / HRD) |
| Кто утверждает | CEO Холдинга | HRD Холдинга |
| Роли | Админ C&B, C&B компании, HR, Руководитель, Участник, Владелец факта, Комитет, Сисадмин | HRD Холдинга / компании / дивизиона, HRBP, C&B |
| Кто вводит факт | Финблок + руководитель | HRBP, HRD компании, C&B |
| Личный кабинет сотрудника | Есть | Нет |
| Дашборд комитета | Есть (рисунок 10.2) | Нет (есть дашборд каскадирования) |
| Каталог | Код, периодичность, источник, владелец, версии, статусы | Только название, ед. изм., ССП, RCD, метод |
| Создание карты | Шаблон по должности / копия прошлого цикла | Каскад / пустая |
| Карты Холдинга и компаний | Упомянуты только в каскаде | Отдельные карты со своим согласованием |

| Пирамида по функциям с «долями» | Нет | Есть |
| Формулы расчёта | Описаны | Реализованы так же |

Похоже, мокап в docx (рисунок 10.1, маршрут «Сотрудник → Руководитель → HR → CEO», подпись «STI 2026») — более ранняя или «эталонная» версия, а HTML-MVP — более поздняя итерация, пересобранная под пилот на функции HR. **Это нужно подтвердить у заказчика.**

## 10. Текущее состояние BI DAMU — существующая страница «Мои KPI»

Страница появилась в коммите `1a388bc` от 21.10.2026 — через неделю после ТЗ, но, судя по содержимому, сделана не по нему.

- Пункт сайдбара: «Мои KPI» (`/dashboard/my-kpi`, иконка `track_changes`) в `app/src/components/Layout.jsx`.
- Страница: `app/src/pages/Dashboard/MyKPI.jsx`.
- Данные: `app/src/data/kpiData.js`.
- Ключи localStorage: `kpi:tasks`, `kpi:status`, `kpi:idp`.

### 10.1. Что на странице сейчас
- **Задачи KPI по 4 блокам:** Fin · Client · Business Process · HR. Комментарий в коде: «стандарт для топ-100 Холдинга».
- 7 демо-задач: план, факт, вес, единица измерения. Название и единица — свободный текст.
- **Статусы:** Черновик → На согласовании → Утверждено.
  - В черновике сотрудник **сам** задаёт задачи, планы и веса. Сумма весов должна быть 100%, план больше 0.
  - Кнопки «Согласовать (демо: руководитель)», «Вернуть в черновик», «Пересоздать KPI (демо)».
- После утверждения сотрудник **сам** вносит факт.
- **Расчёт:**
  - выполнение задачи = факт / план, с ограничением **0–100%**;
  - итог = Σ(выполнение × вес) / 100;
  - пороги «Достигает» от 90%, «Под риском» 70–90%, «Не достигает» ниже 70%.
- **Виджеты:** кольцо общего выполнения, прогресс по блокам, «Риски» (задачи ниже 70% и просроченные пункты IDP).
- **Блок IDP** (индивидуальный план развития): пункты из оценки 360 с привязкой к компетенции и личные задачи (пример «Пробежать марафон»), чекбоксы, сроки, добавление своих пунктов.

### 10.2. Отличия текущей страницы от ТЗ

| Тема | Сейчас в «Мои KPI» | По ТЗ / макету |
|---|---|---|
| Группировка | Блоки Fin / Client / Business Process / HR | Перспективы ССП: Финансы / Клиенты / Процессы / **Обучение и развитие** |
| Источник KPI | Свободный текст | Выбор из **каталога KPI** (ведёт C&B) |
| RCD (RUN/CHANGE) | Нет | Есть |
| Метод расчёта | Только прямой | Прямой / **обратный** / бинарный / качественный. Например, «Текучесть ИТР» по смыслу обратный, а считается сейчас как прямой |
| Ограничение исполнения | 0–100% | **80–120%**: ниже 80 → 0, выше 120 → 120 |
| Итог | Без ограничений, пороги 90 / 70 | **50–120%**, ниже 50% — STI не выплачивается. Цвета: < 80 / 80–100 / ≥ 100 |
| Кто составляет карту | Сотрудник | Руководитель (ТЗ) или HR (макет) |
| Кто вводит факт | Сотрудник | Финблок и руководитель (ТЗ) или HR и C&B (макет) |
| Согласование | Один демо-шаг «руководитель», без комментария | Многоэтапный маршрут, возврат только с комментарием, история |
| Утверждённая карта | «Пересоздать KPI» возвращает её в черновик | Блокируется навсегда |
| Факт по периодам | Одно значение | Ежеквартально + год |
| КТУ, бюджет БФ, сумма к начислению, «Жулдызай» | Нет | Есть |
| Каскад от уровня выше | Нет | Ключевая функция |
| Печатная форма | Нет | Есть |
| IDP | **Есть** | **В ТЗ и HTML-макете нет** |
| Цикл | Сроки IDP в 2026 году | Цикл 2027 |
| Аудитория | «топ-100 Холдинга» | «~200 сотрудников с бонусным фондом» |

**Вывод.** Текущая страница — ранний концепт личного кабинета (виджеты, блоки, IDP). Расчёт и роли нужно переделать под ТЗ. Из страницы можно сохранить:
- общую раскладку и виджеты — подходят под «Личный кабинет сотрудника» из ТЗ 5.6;
- проверку суммы весов = 100%;
- блок IDP, если заказчик подтвердит, что он нужен в разделе KPI.

### 10.3. Остальное в приложении
- В приложении уже есть разделение по ролям: `/admin` (RoleGuard `admin`), `/hr` (RoleGuard `hr`), ключ `auth:roles`. На это можно опереться для ролей KPI.
- Тип плана `'KPI'` в `PLAN_TYPES` (`app/src/pages/MyPlans/index.jsx`) с разделом KPI никак не связан.
- Бэкенда нет, данные в localStorage — так же, как в HTML-макете.

### 10.4. Где это может жить (предложение, не решение)
| Часть | Куда |
|---|---|
| «Мои KPI»: своя карта, ознакомление, история, IDP | Существующий пункт сайдбара — переделать |
