## 2. Роли и доступ

| Роль | Что видит |
|------|-----------|
| `employee` | Профиль, планы, навыки, карьерный трек. Запрашивает аттестацию, подтверждает навыки, подаёт заявки на обучение |

## 4. Ключевая логика существующих экранов

### CareerMap (`src/pages/CareerMap.jsx`)

Самый большой файл. Режим `buildTo === null` — стандартный вид (Foreman A → B → цель по центру); `buildTo !== null` — режим исследования, DFS по `CAREER_GRAPH`.

- `CURRENT_POSITION`, `CAREER_GRAPH`, `NEXT_GOAL_OPTIONS`, `GOAL_TO_PLAN_ID` — сейчас хардкод, уходят на `GET /api/career-graph?clusterId=`
- `findAllPaths` (DFS) + `computeLayout` (разбивка на prefix/branches/suffix) + `ForkConnector` (SVG-развилки) — чистая фронтенд-логика, бэкенд не участвует
- Кнопка «Установить карьерную цель» — только на карточках из `NEXT_GOAL_OPTIONS[CURRENT_POSITION]`, не текущая цель. Диалог подтверждения — локальный `confirmGoal`

### MyPlans / CareerPlanDetail

- `MyPlans/index.jsx` — читает `careermap:goal` из localStorage, динамически формирует название плана. Уходит на `GET /api/me/plans`
- `CareerPlanDetail.jsx` — три вкладки (требования, план обучения, готовность к оценке). Вкладка готовности считает обязательные пункты из `LEARNING_PLAN`, исключая `'Рекомендуемые курсы'` и пункты с `'казахский'` в названии

### Ключи localStorage (уйдут при переходе на API/сессию)

| Ключ | Где | Назначение |
|------|-----|-----------|
| `careermap:goal` | CareerMap, MyPlans, CareerPlanDetail | Текущая карьерная цель |
| `careermap:zoom` | CareerMap | Масштаб карты |
| `careermap:tour-seen` | CareerMap | Онбординг-тур завершён |
| `theme:dark` | ProfileContext | Тёмная тема |
| `auth:roles` | useRole | Роли пользователя (заменится на Keycloak-токен) |

## 6. Состояния экрана (сейчас отсутствуют в прототипе)

Каждый экран с данными из API должен реализовать три состояния:
- **Загрузка** — скелетон/спиннер, не пустой экран
- **Пусто** — например, нет навыков на подтверждение, нет уведомлений — не путать с ошибкой
- **Ошибка загрузки** — с возможностью повтора запроса

---

## 7. Требования ИБ (фронтенд-часть)

- Токен Keycloak — в памяти или httpOnly cookie, **не в localStorage** (XSS)
- `RoleGuard` — скрывает меню/роуты, но не заменяет серверную проверку. Не полагаться на него как на защиту данных
- Не показывать чужие данные по прямому URL-параметру (`employeeId` в query/body игнорируется бэкендом — приходит из токена), но и на фронте не строить ссылки на чужие профили без проверки роли
- Файлы (сертификаты, аватары) — только по подписанным S3-ссылкам с TTL, не хранить прямые постоянные URL

## 9. Новое: три сущности UnityBPM — что нужно фронтенду

Бизнес-флоу подробно разобран в [BPM_INTEGRATION.md](BPM_INTEGRATION.md). Ниже — что из этого требует изменений/новых экранов на фронте.

### 9.1 Подтверждение навыка — изменение существующего экрана

> **Обновлено 31.07.2026.** Логика подтверждения навыков полностью пересмотрена 23.07.2026 (см. BACKEND_SPEC.md, `employee_skills`). Ниже — итоговое состояние `MySkills.jsx`/`SkillDetail.jsx` после приведения прототипа в соответствие с этим решением.

- **`LevelBar`/CEFR-бейдж стали read-only (исправлено 31.07.2026).** Раньше сотрудник мог кликнуть любой квадратик шкалы 1–4 (или выбрать CEFR из дропдауна) и мгновенно выставить себе любой уровень — это прямо противоречило решению от 23.07 («сотрудник вообще не подтверждает навык сам ни на одном уровне»). Теперь `LevelBar`/`CefrBadge` — чистое отображение текущего уровня, без `onClick`/`onChange`. Уровни 1–3 в прототипе остаются статичными демо-данными (реальная логика — событие от BILIM/TestLab, которое эмулировать в чистом фронтенде нечем без бэкенда).
- **Новое действие — «Запросить эксперта».** Единственное, что сотрудник может сделать руками — запросить подтверждение уровня 4 (Эксперт), и только когда уровень уже равен 3. Кнопка «Запросить эксперта →» показывается именно в этом случае (`skill.level === 3 && !skill.expertPending`); после клика показывается бейдж «Ожидает эксперта» вместо кнопки. Дальше в прототипе ничего не происходит — нет экрана «Руководитель», который мог бы обработать эту заявку (роль ещё не заведена в системе, см. TASKS.md), так что заявка остаётся в статусе «ожидает» — это ожидаемое ограничение демо, аналогично другим «зависающим» pending-статусам в прототипе (заявка на аттестацию, на обучение).
- **Флаг `selfDeclared` переосмыслен, не переименован.** Технически поле в данных всё ещё называется `selfDeclared`, но в UI это больше не «самозаявленный навык» — иконка сменилась со звезды на песочные часы, подпись — на «Ожидает подтверждения (BILIM/TestLab)» (звезда теперь однозначно означает только избранное).
- При отображении статуса `rejected` у навыка теперь всегда приходит непустой `comment` (обязателен на стороне BPM для уровня 4; для 1–3 отклоняет TestLab). Показать его сотруднику как причину отказа, а не просто статус «Отклонён» без пояснения. **Пока не реализовано в прототипе** — статус `rejected` нигде фактически не выставляется, т.к. нет реального TestLab/BPM.
- **Избранное и целевые навыки — фильтрация уже работает в прототипе** (локально, не через API): `FILTERS = ['Все', 'Избранные', 'Подтверждённые', 'Целевые']` фильтрует и хардкод-навыки, и добавленные вручную. Для бэкенд-интеграции подключить к `GET /api/me/skills?group=` и `PATCH /api/me/skills/:id/favorite` — см. BACKEND_SPEC.md, раздел 5.1, и раздел 4 (`employee_skills`, поле `is_favorite`, вычисляемый `isTarget`).
- **Навыки вне карьерного трека — реализовано в прототипе 31.07.2026.** Точка входа — кнопка «В план ▾» в каталоге `/skills` (список и деталка навыка), а не «+ Добавить навык» на `MySkills` (та кнопка так и осталась декоративной, не трогали). Клик пишет навык в `myskills:custom` (localStorage) с `level: null`; `MySkills.jsx` читает этот ключ и рендерит навыки отдельными группами по категории каталога, с бейджем «Добавлено вами». Как только в каталоге навык уже добавлен, кнопка меняется на «✓ В плане» (задизейблена).
  - Добавлена новая категория каталога **«IT и цифровизация»** (Python, SQL и базы данных, Основы DevOps, Кибербезопасность: базовый уровень, Управление IT-проектами) — как пример навыка вне обычного строительного трека.

Механизм `skill:myLevel:*` полностью убран 31.07.2026 — `SkillDetail.jsx` теперь читает/пишет уровень через тот же `myskills:custom`, что и `MySkills.jsx` (раньше это были два независимых, несинхронизированных мини-стора).

Поскольку `LevelBar` теперь read-only и уровни 1–3 в демо взяться неоткуда (нет BILIM/TestLab), на практике у самостоятельно добавленных навыков кнопка исключения в прототипе будет доступна всегда, пока не подключена реальная интеграция — это ожидаемое, а не ошибочное поведение демо. См. правило `DELETE /api/me/skills/:skillId` в BACKEND_SPEC.md, раздел 5.1.
  - Подтверждение таких навыков (BILIM/TestLab/эксперт) — тот же пайплайн, что и для целевых, без исключений (решено, см. TASKS.md/TZ_BACKLOG.md) — в прототипе кликабельна только часть про уровень 4 («Запросить эксперта»), 1–3 остаются демо-данными до реальной интеграции.
- **Каталог `/skills`: убрана вкладка «Рекомендуемые», починено и объединено избранное (31.07.2026).**
  - «Рекомендуемые» убрана — критерий рекомендации нигде не был определён в ТЗ (похоже, перекочевала из референсного продукта, см. rules.md). Осталось «Все навыки» / «Избранные», обе теперь реально фильтруют список.

  - **Семантика счётчика «+N добавили» (решено 31.07.2026):** должен учитывать только добровольные действия (добавление в план / избранное), не автоматическое присутствие навыка как целевого по должности — иначе счётчик просто отражает распространённость должности, а не реальный интерес к навыку. В прототипе `POPULARITY` остаётся статичными демо-числами (агрегат по компании, не по текущему пользователю) — реальный подсчёт по этой семантике реализуется на бэкенде, см. BACKEND_SPEC.md, `skills.added_count`.

### 9.2 Аттестация — новый статус и новое сообщение

`Assessment` (история) и виджет на `MyDashboard`:

- Новый промежуточный статус **«Ожидает аттестацию»** между «На рассмотрении у HR» и «Завершена» — участники комиссии добавлены в BPM, но встреча ещё не проведена. Дату/место система не знает (назначается HR офлайн через Outlook) — не пытаться показать дату, только сам статус
- При `outcome = passed` — помимо «Прошёл аттестацию», нужно показать пояснение **«На скамейке»** (ждёт открытую позицию) — текстовый бейдж/тултип, не блокирующий остальной интерфейс
- `AssessmentEntry` (HR, ввод оценки) — без изменений в форме, но после сохранения результата бэкенд теперь также решает `outcome`; фронту достаточно показать сообщение об успешном сохранении, никакой новой логики на этом экране не требуется

### 9.3 Заявка на обучение

**А. Сотрудник — подача заявки (частично есть, не сохраняет данные)**
- В `ExperienceProfile` уже реализована заготовка: предупреждение об истёкшем сертификате (блок сертификатов) → кнопка **«Записаться»** → модалка (дата желаемого прохождения, комментарий) → `submitEnroll`
- Проблема: `submitEnroll` только показывает экран «Заявка отправлена», ничего не сохраняет — нет ни localStorage, ни какого-либо стора заявок. Нужно завести `training:requests` (по аналогии с `hr:training-requests` в `AddCertificate.jsx`) и реально писать туда запись при отправке
- Также должна быть доступна самостоятельная подача (не только по истечению) — где именно разместить точку входа (`MySkills`? отдельный пункт меню?) — решить при дизайне, сейчас не определено
- Новая вкладка/секция истории заявок (аналог `Assessment` для аттестаций) — статусы `pending` / `matched` / `completed` / `rejected` / `withdrawn` — **пока не реализована**, из `rejected`/`withdrawn` — кнопка «Подать заново»
- Отзыв заявки («Отозвать») происходит в BPM, не на фронте Damu — на этом экране только отображение статуса, действия отзыва здесь не будет

**Б. HR-панель — добавить сертификат сотруднику (реализовано)**
- `/hr/certificates` (`AddCertificate.jsx`): поиск/выбор сотрудника → форма сертификата (название, кем выдан, дата получения, дата истечения, ссылка на файл)
- Перед сохранением — проверка на совпадение с `hr:training-requests` (заменится на `GET /api/hr/training-requests/match-check`); при совпадении — диалог **«У сотрудника уже есть поданная заявка. Подтвердить этим сертификатом?»** (привязать / завести отдельно)
- Список добавленных сертификатов на той же странице: статистика (всего / за месяц / привязано к заявкам), поиск, статус срока действия
- `/hr/employees` (`Employees.jsx`): справочник сотрудников с поиском/фильтром по кластеру, кнопка «+ Сертификат» ведёт на `/hr/certificates` с уже выбранным сотрудником (`location.state.employee`)
- Данные пока в localStorage, список сотрудников — хардкод `MOCK_EMPLOYEES` (дублируется в обоих файлах, не общий модуль) — при подключении API заменить на `GET /api/hr/employees`

**Профиль опыта (`ExperienceProfile`)** — блок сертификатов должен отображать дату получения с разбивкой по кварталам (Q1–Q4), независимо от источника (LMS или ручной ввод HR). Сейчас сертификаты, добавленные HR через `/hr/certificates`, никак не попадают в `ExperienceProfile` сотрудника — это два независимых localStorage-стора без связи. При переходе на реальный API это решится само (общий бэкенд), но пока это две разные, не синхронизированные заготовки.
