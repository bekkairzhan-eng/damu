## 1. Роли в системе

| Роль | Кто | Что может |
|------|-----|-----------|
| **Сотрудник** | ИТР (Foreman, Site Manager и др.) | Смотрит свой профиль, подтверждает базовые/средние навыки сам, запрашивает аттестацию |
| **Руководитель** | Прямой руководитель сотрудника | Подтверждает продвинутые навыки подчинённых, видит профили своей команды, получает уведомления по команде |
| **Эксперт предметной области** | Специалист в конкретной области | Подтверждает навыки уровня «Эксперт» в своей зоне ответственности |
| **HR-партнёр** | HR, закреплённый за подразделением | Управляет матрицей навыков, собирает комиссию аттестации, исполняет задачи в БПМ |
| **Администратор** | Системный администратор | Управляет справочниками (должности, навыки, подразделения), назначает роли пользователям |

Авторизация — через Keycloak (SSO). Разработчик настраивает на старте.

## 2. Логика подтверждения навыков

> **Пересмотрено по итогам встречи с заказчиком 23.07.2026** (замечание Дильдар). Раньше уровни 1–2 сотрудник подтверждал сам без внешнего апрува — это оказалось неверным решением, отменено. Теперь сотрудник не подтверждает сам ни один уровень.

Каждый навык в матрице имеет 4 уровня: **Базовый → Средний → Продвинутый → Эксперт**.

Подтверждение теперь идёт разными источниками в зависимости от уровня, а не по единой метке «кто подтверждает»:

| Уровень | Кто/что подтверждает | Механизм |
|---------|------------------------|----------|
| 1 — Базовый | **BILIM** (LMS) | Автоматически, по результатам курса/теста внутри BILIM |
| 2 — Средний | **BILIM** (LMS) | Автоматически, аналогично уровню 1 |
| 3 — Продвинутый | **TestLab** (новая система тестирования) | Через тест TestLab, привязанный админом к навыку (см. ниже) |
| 4 — Эксперт | Эксперт / непосредственный руководитель | Вручную, единственный уровень с ручным апрувом через UnityBPM |

**Механика подтверждения уровня 3 — решено 07.08.2026.** В каталоге навыков админ привязывает к навыку конкретный тест из справочника тестов TestLab (выбор из списка, не ссылка). Проверка — не в реальном времени, а отдельным процессом раз в полгода (не ночной батч рейтинга): прошёл ли сотрудник привязанный тест → если да, уровень 3 подтверждается автоматически. Подробности — [TASKS.md](TASKS.md#логика-подтверждения-навыков-по-уровням).

Точный триггер подтверждения в BILIM (завершение курса? проходной балл теста?) — не определён. Контракт с самим TestLab (как считается «прошёл» конкретный тест) — тоже не определён, требуют отдельной проработки с командами этих систем перед реализацией интеграции.

### Статусы навыка после действия сотрудника:

| Статус | Когда | Отображение |
|--------|-------|-------------|
| ⏳ **Ожидает подтверждения** | Уровень задан, ждём ответа от BILIM / TestLab / эксперта | Жёлтый, в прогресс не засчитывается до подтверждения |
| ✅ **Подтверждён** | Пришёл положительный результат от BILIM / TestLab / эксперта | Зелёный, засчитывается в прогресс |
| ❌ **Отклонён** | TestLab — не пройден порог, либо эксперт отклонил (уровень 4) | Отображается с комментарием (для уровня 4 — обязателен всегда, см. ниже) |

### Флоу подтверждения:
1. Сотрудник указывает уровень навыка
2. Для уровней 1–3 — статус **Ожидает подтверждения**, результат приходит автоматически от BILIM/TestLab, без участия сотрудника или ответственного лица
3. Для уровня 4 — сотрудник нажимает «Подтвердить навык», заявка уходит эксперту/руководителю в BPM
4. Эксперт нажимает «Подтвердить» или «Отклонить» — **комментарий обязателен в обоих случаях** (раньше был обязателен только при отклонении; расширено по итогам встречи 23.07.2026)
5. Сотрудник получает уведомление о результате с комментарием эксперта в любом случае

## 2.1 "Мои навыки" — группировка (пробел в ТЗ, найден при ревью 31.07.2026)

Экран сотрудника «Мои навыки» делит навыки на 4 группы, которая раньше нигде не была описана в бизнес-логике — только в UI-прототипе:

| Группа | Логика |
|--------|--------|
| **Целевые** | Навык требуется на текущей или целевой должности сотрудника (в его кластере) — вычисляется, а не хранится отдельным полем. Включает навыки, которые ещё не начаты (уровень не выставлен) |
| **Подтверждённые** | Навык подтверждён (`статус = confirmed`) — независимо от того, целевой он или нет |
| **Избранные** | Свободно переключаемая пометка, не связанная ни с целевыми, ни с подтверждёнными — сотрудник может добавить в избранное любой навык из каталога, даже не относящийся к карьерному треку |
| **Все** | Все целевые навыки (включая ещё не начатые) + все навыки, которые сотрудник когда-либо добавил себе (включая не относящиеся к карьерному треку) |

**Ключевое уточнение:** сотрудник может добавить в свой профиль навык, который не входит в требования его должности — просто потому что захотел его освоить (сам объяснил: «почитал, освоил, никто не должен ограничивать»). Это не запрещено моделью.

~~**Открытый вопрос:** должен ли такой навык (вне карьерного трека) проходить подтверждение так же, как целевой?~~ — **решено 31.07.2026:** да, тот же пайплайн (BILIM/TestLab/эксперт), без исключений.

**Исключение навыка из профиля — решено 31.07.2026.** Убрать самостоятельно добавленный навык можно только пока уровень не выставлен вообще (в т.ч. Базовый) — как только выставлен любой уровень, исключить нельзя ни при каком статусе. Специально упрощено: раз уровня нет, заявка на подтверждение никуда не отправлялась, отменять нечего (в отличие от заявки на обучение, где для этого есть статус `withdrawn`). Целевые навыки исключить нельзя никогда — это вычисляемое свойство, требование должности всё равно останется видно как пробел.

**Реализовано в прототипе 31.07.2026:** кнопка «В план ▾» в каталоге `/skills` (была декоративной) добавляет навык в «Мои навыки» без уровня; кнопка ✕ там же исключает его, пока уровень не выставлен. Добавлена категория каталога «IT и цифровизация» — навыки вне обычного строительного трека (Python, SQL, DevOps и т.д.).

**Исправлено 31.07.2026 (найдено при ревью):** шкала уровня 1–4 в прототипе была свободно кликабельной — сотрудник мог сам выставить себе любой уровень, вопреки решению из раздела 2 («сотрудник не подтверждает сам ни один уровень»). Теперь шкала только отображает текущий уровень; единственное ручное действие сотрудника — кнопка «Запросить эксперта», доступная лишь когда уровень уже равен 3 (Продвинутый).

**Каталог «Навыки»: убрана вкладка «Рекомендуемые», избранное объединено (31.07.2026).** «Рекомендуемые» убрана — критерий рекомендации нигде не был определён. Иконка избранного в каталоге раньше по клику открывала деталку навыка вместо переключения избранного — починено. Избранное теперь общее состояние для каталога, деталки навыка и «Мои навыки» (раньше — три независимых, часто вообще не сохраняющихся переключателя).

**Кнопка «В план» → статус-текст, если уже добавлен (31.07.2026).** Если навык уже входит в профиль (целевой или добавлен самостоятельно), кнопка «В план» больше не показывается вообще (даже задизейбленной) — вместо неё текст «✓ Уже в ваших навыках».

**Счётчик «+N добавили» (31.07.2026):** считает только добровольные действия — добавление в план или в избранное. Навыки, присутствующие у сотрудника только как целевые (обязательные для должности), в счётчик не входят.

**Пересмотрено в тот же день (31.07.2026):**
- Избранное из каталога «Навыки» убрано обратно — это инструмент только для «Мои навыки» (фильтровать среди своих уже добавленных навыков). В каталоге позже появятся другие фильтры вместо «Избранные» (например, по семейству должностей).
- Уровень нового навыка при добавлении «в план» — явно `0` («не начат»), не `null`. Подтверждено: уровень 4 (Эксперт) нельзя запросить без подтверждённого уровня 3 (Продвинутый) — так и было реализовано.
- Убрать самостоятельно добавленный (не целевой) навык теперь можно не только с «Мои навыки», но и прямо из каталога/деталки навыка — везде, где он показан как уже добавленный, только пока уровень = 0.

## 3. Аттестация (интеграция с БПМ)

### Флоу:
1. Сотрудник в разделе «Аттестация» нажимает **«Запросить аттестацию»**
   - Доступно только если: % выполнения плана ≥ **85%** и ключевые навыки подтверждены
2. Система находит HR-партнёра, закреплённого за подразделением сотрудника (данные из БПМ)
3. В БПМ на HR падает задача: _«Сотрудник [ФИО], должность [X], заявил готовность к аттестации на [целевую должность]»_
4. HR в БПМ:
   - Добавляет членов комиссии (выбирает людей)
   - Проверяет доступность слотов у всех участников
   - Бронирует аудиторию
   - Нажимает **«Исполнить»**
5. Сотрудник получает уведомление: дата, время, место аттестации
6. На главной странице сотрудника появляется виджет «Ближайшая аттестация»
7. После аттестации HR фиксирует результат в БПМ → данные приходят в BI DAMU → статус плана обновляется

### Данные из БПМ:
- Оргструктура (кто чей руководитель, кто HR подразделения)
- Результаты аттестаций

## 5.1 Должности: «Общие требования», грейды, ссылка на Базу знаний (решено 12.08.2026)

**«Общие требования»** — текст по категориям на каждую должность (что ожидается от сотрудника: работа с заказчиком, управление командой, строительные практики, ответственность, отчётность, опыт). Заводит **администратор** per-position. Раньше это был generic-хардкод во фронтенде, не связанный ни с админкой, ни с id должности.

**Категории — общий справочник для всех должностей** (не свой набор у каждой). Отсюда правило: добавили категорию → она обязательна к заполнению у каждой должности. Требования к реализации:
- сохранить должность с пустым полем нельзя — валидация на бэкенде (422), не только на фронте;
- по каждой должности отдаётся счётчик заполненности («5/7») для админки;
- админ видит список должностей, где не всё заполнено;
- удаление категории удаляет тексты по ней у всех должностей, с предупреждением.

**Грейды — источник правды HRMS, через Kafka.** В Damu только чтение, админ не редактирует. Должности уже синхронизируются; грейды — следующий шаг интеграции (связать с должностями). До этого решения грейды расходились между экранами прототипа.

**Ссылка «Читать в Базе Знаний»** ведёт в пространство Damu в Базе знаний. URL заводит админ per-position.

**Зарплатные вилки** — показывать ли сотрудникам на странице «Должности», не решено. См. [HRD_QUESTIONS.md](HRD_QUESTIONS.md#должности), вопрос №11.

## 3.1 Подтверждение проекта (опыта работы) — новая сущность

> Зафиксировано по итогам встречи с заказчиком 23.07.2026. Полное описание флоу — [BPM_INTEGRATION.md, раздел 4](BPM_INTEGRATION.md#4-подтверждение-проекта-опыта-работы).

Контекст от HRD: разброс по опыту сотрудников большой — ~40% Foreman'ов (молодые, 22–25 лет) успели сдать всего 1–2 объекта, ~10% — со стажем от 5 лет. Компании нужно реально собрать и подтвердить вклад каждого сотрудника в проекты.

- Сотрудник добавляет проект в «Профиль опыта» вручную, как и раньше (форма не меняется)
- Каждый добавленный вручную проект уходит **отдельной задачей HR-партнёру** в UnityBPM — HR подтверждает участие сотрудника в проекте офлайн (кадровые документы, созвоны с причастными), **по одному проекту за раз**, не пакетно
- Статус проекта: `pending` → `confirmed` / `rejected`
- Как только заработает интеграция с SuperApp — **новые** проекты будут приходить оттуда автоматически, без участия HR и без прохождения через этот BPM-флоу; ручное подтверждение HR останется только для проектов, введённых сотрудником до этой интеграции
